# Stable native entry and deployment

The native implementation targets .NET Framework 4.8. Its app-owned `SiemensMCPServer.NativeLauncher.exe` uses a separate Framework AppDomain with the selected immutable runtime's application base and binding redirects, in the same OS process and inherited stdio pair. It does not use the .NET 8 offline loader or its one-process limit. The native host owns the parent/EOF fence, session admission, private-worker Job and exact attachment/resource ledger.

The native launcher has a fixed ABI identity independent of app timestamps. It verifies a strict hash-pinned selection, exact bounded runtime inventory, ordinary contained paths and open read leases. A pointer update affects new roots; live roots retain their selected generation. The runtime AppDomain remains until process exit because its retained unmanaged parent wait cannot be unloaded reliably after SDK EOF. There is no child MCP process or transport-forwarding wrapper.

New candidates store bundled workers and guidance in two indexed ZIPs in the immutable selected runtime. The unchanged stable launcher verifies and holds read leases on both complete archive files. Guidance readers enforce revision/content pins and bounded decoding. Workers expand only after execution admission into a new private cache directory; each member is checked against the archive index, bundled registries/manifests remain pinned to that index, and execution holds read leases on the staged payload until the original worker is confirmed gone. A failed expansion retains its partial evidence and refuses another expansion in the same root. The earlier directory layout remains supported. Source/package checks do not establish concurrent startup timing or installed acceptance. Reviewed extension updates use the separate app-owned `extensions/` root and existing generation/hash-checked staging and reload tools. Never edit selected runtime bytes to reload features. Under the eight-process default, reload one named module at a time so replacement workers fit beside the retained generation; a capacity failure preserves the active generation.

`build/Install-StableNativeMcp.ps1` stages verified native packages under a persistent app-owned root, resolves physical MSIX paths from the opened publication lock, retains immutable runtimes/selection backups, and derives a standalone plugin with four native skills and an absolute stable command/cwd. Existing launcher asset bytes must match. The installer never starts MCP/TIA, edits Codex settings or changes immutable Codex caches.

Siemens persistent Openness approval records the executable path, SHA-256 and UTC modification time. Keep the stable launcher at its approved physical path without replacing or touching it during backend/worker updates. Loading a backend in the same OS process preserves that executable identity. A different launcher, helper, installation path or TIA-version whitelist may need its own approval. Siemens documents that **Yes** permits one connection and **Yes to all**, followed by UAC approval, persists an entry. See the [Openness firewall documentation](https://docs.tia.siemens.cloud/r/en-us/v20/tia-portal-openness-api-for-automation-of-engineering-workflows/tia-portal-openness-api/general-functions/tia-portal-openness-firewall).

Normal selection requires an exact-package receipt for metadata, pure workers, disposable native edit/readback, compile, save/reopen/restore and no outstanding uncertainty:

```powershell
.\InstallMcp.cmd -Native -Package 'C:\packages\native.zip' -AcceptanceReceipt 'C:\private\accepted.json' -AllowWrites -NoPause
```

`-PilotOnly` requires a distinct explicit private installation root and does not authorize normal publication. Launch writes remain off unless selected explicitly. New candidates separate discovery and execution admission. Normal defaults allow 32 discovery connections, each initially limited to one process / 128 MiB committed Job memory. Initialize, fixed tool schemas, pinned guides and doctor require no execution slot or feature worker. Version selection/installed-version listing also avoids execution admission.

Native API calls, feature discovery/reload and local analysis require one of four active workspace slots before dispatch. Admission expands only that root's Job to its configured execution ceiling, normally eight processes / 1024 MiB. Two local analysis lanes and 64 shared durable resource claims remain separate limits. A full workspace pool refuses work while leaving lightweight discovery connected. The workspace retains native selection, previews and workers until explicit `tia_detach` or EOF. Detach drains local/native work, detaches without saving, invalidates previews and stops its own workers. It releases execution admission and returns to one process / the discovery memory ceiling only after workers have exited and root memory fits. Otherwise the result reports retained execution; it does not force memory down or stop peers.

Execution uses the earlier native slot namespace. Retained older roots still charge the execution pool until they exit naturally, even if they are idle; there is no mass restart or silent increase in native execution capacity. For example, three older roots leave one of four workspace slots available to new candidates. Discovery has its own namespace. The steady default hard envelope is at most 32 roots and 60 processes, with at most four expanded workspace Jobs: 28 × 128 MiB + 4 × 1024 MiB = 7.5 GiB committed Job ceilings. This is a ceiling, not reserved or measured typical memory. During transition, up to four roots from the earlier four-frontend/eight-process/1024 MiB policy may coexist with 32 new roots. Because those older roots also consume the shared execution slots, that specific transition is bounded by 36 roots, 64 processes and 8 GiB Job ceilings. Different configured policies need their own accounting; measure the retained peers and preserve them.

Initial pilot policy uses one discovery connection, one workspace, one analysis lane, eight owned resources/processes and a 1024 MiB execution Job. Exact retained TIA claims prevent competing attachments. All admission/memory limits remain GUI editable; new discovery fields have defaults when reading earlier policies, and existing policy files are preserved. Candidate/package/installed/native acceptance remain separate; consult the exact installation receipt before attributing new behavior to an older root.

Use the returned `safeguardsFile` with the desktop GUI's `--safeguards --settings-file=<path>` to edit native policy. Launch permission, policy, explicit native target, preview/fingerprint/candidate checks and uncertainty barriers apply together. Compile/save/reopen remain separate operations. Attached external TIA is never assigned to the worker Job or stopped by detach/EOF. A disposable fixture that creates its own TIA needs a separately reviewed budget and exact ownership; the worker budget is not proof that TIA itself fits in 1 GiB.

After native acceptance, publish exactly one resolved host route with serialized settings ownership, byte backup, validated TOML, compare-and-swap and readback. Preserve unrelated settings, active old offline roots, rollback packages and uncertainty records. Verify the installed stable route's actual tool schemas, pinned guide and disposable edit/readback after plugin/loader selection. CLI discovery is not proof of an already-open chat's activation. Unified/PLC/runtime acceptance remains target-specific.
